# GEB 使用与维护指南

本项目的 GEB 指渐进式项目导航：AGENTS → L1 → L2 → 必要的 L2-2 → 文件头 L3 → 实际代码。它解释现有项目，不要求重构出理想目录。

## 阅读与信息所有权

先确认仓库、分支、工作树与适用规则，再从 [L1](../L1.md) 选任务区域。进入相关目录地图，读文件头、实现、调用方和验证入口。地图有误时按代码核实，不能以文档替代证据。

| 位置 | 维护内容 |
| --- | --- |
| AGENTS | 协作、界面和开发约束 |
| L1 | 项目骨架、主要链路、外部系统和任务路由 |
| L2／L2-2 | 目录或稳定子能力的职责、输入输出、依赖、状态与失败边界 |
| L3 | 重要文件的短坐标，唯一维护在文件头 |
| README／专项 README | 用户能力、安装、包用法和操作步骤 |
| 开发导航 | 验证命令、环境前提和任务索引 |
| 工作区交接／日志 | 阶段进度与历史，正式地图不复制本机状态 |

## 按影响更新

- 局部算法不改变契约：改实现与适当验证，核对 L3；上层事实未变则不制造地图 diff。
- 输入输出、副作用或失败语义变化：先校准 L3，再检查所属地图与消费者。
- 新增／移动／删除文件：检查静态与动态引用、资源路径和导出，补直接地图；新核心边界文件登记检查范围。
- 跨域契约或持久格式变化：同步生产者、消费者与兼容策略，核对 L2；系统流向变化才更新 L1。
- 新稳定子能力：确认职责和变化原因，才增加 L2-2。目录变大或文件很多不单独构成加层理由。

`src/lib` 含构建和浏览器代码，SSR 会引用 Lit，配队数据有运行时回边，私有媒体包引用 Worker 权限。这些是需要维护的实际边界，不能靠地图画成单向依赖，也不因维护地图自动实施解耦。

## 编写 L3

沿用语言合法的短注释，通常包含 `Input`、`Output`、`Pos`、`Effects/Dependencies`。Pos 链接直接地图；不复制完整 import、函数列表、调试过程或未来拆分计划。

```text
// L3 — GEB
// Input: 实际参数、配置、数据与状态。
// Output: 实际接口／结果和重要失败状态。
// Pos: [Map](直接所属地图相对路径)；本文件在域内的职责。
// Effects/Dependencies: 网络、文件、缓存、进程或环境依赖；注明按调用发生的副作用。
```

Python 使用 `#`。保留 BOM、换行、shebang、编码、原有许可、模块 docstring、future import 与 TS reference 指令。Astro 若需文件坐标，应放进合法 frontmatter，不把注释显示给读者。类型入口、普通小文件、JSON、SQL、样例、翻译目录、生成物和第三方源码不机械加头。

核心覆盖登记在 [geb-scope.json](geb-scope.json)，只存路径、父图与排除政策，不保存第二份 L3 正文。新增有架构意义的入口或 I/O 边界时，补头与路径登记；外部仓库在各自版本范围维护。

## 检查与交付

命令见 [开发导航](DEV_GUIDE.md)。检查器验证地图存在、父子可达、局部 Markdown 路径与锚点、核心 L3 和源文件的就近地图归属。用 `--base` 验证纯文档／注释变更时，检查既有可执行源码只新增规范 L3，Python AST 保持一致；它不是未来业务变更的默认要求。

本地文件链接目标必须存在，并属于 Git 跟踪文件或未被忽略的新文件；只存在于本机的忽略文件不能作为导航目标。带 UTF-8 BOM 的 L3 与普通 UTF-8 一样参与核心登记和坐标检查。

检查器不访问网络、不验证远端页面或 GitHub Checks，也不能判断所有职责文案、动态调用和隐含副作用。文档链接到目录只证明目录存在。交付仍需阅读实际 diff，人工核对关键链路，记录未执行的验证及原因。

只在授权范围内提交、推送或发布；只暂存自己的明确路径。不要加入凭据、用户截图／存档、游戏资源、外部引擎、缓存或研究聊天。正式导航必须在独立仓库内成立，不能引用旁边 bot 或本机绝对路径。达到验收条件后停止扩层。
